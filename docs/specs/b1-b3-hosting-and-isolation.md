## 2. B1 — the project, and the row without which nothing works

Provisioning is half an hour and not interesting. Two details are.

**The migrations were applied as SQL generated by alembic itself** — `alembic upgrade head --sql`,
run offline against the real revision graph, then executed on the project. The generated script
includes the `alembic_version` bookkeeping, so the database is stamped exactly as a connected
`alembic upgrade head` would leave it and the next migration follows normally. This was not
aesthetic: outbound Postgres from the build environment is blocked, so a connected alembic run was
not available. The offline path produces the same statements from the same source, which is the
property that mattered.

**The `channel_configs` row is B1's actual deliverable.** The schema is inert without it:
`ChannelConfigTenantResolver` raises `UnknownEndpoint` rather than guessing a tenant, so a missing
row turns every inbound message into a 500 and a retry storm from Meta. One tenant
(`11111111-1111-4111-8111-111111111111`) and one enabled `whatsapp` row now exist. Its `external_id`
is the literal string `PLACEHOLDER_WHATSAPP_PHONE_NUMBER_ID`, which resolves nothing — replacing it
with the Meta phone‑number id is step 1 of §6 below, and until then the endpoint is unresolvable in
a way that says so.

## 3. B2 — why the role comes before the policies

The obvious way to do RLS is to write the policies and move on. That would have produced a database
that enforced nothing, and the reason is one row of `pg_roles`:

```
rolname   | rolsuper | rolbypassrls
postgres  | f        | t
```

Supabase's `postgres` — the role whose URI the dashboard hands you, the one every "connect your app"
guide pastes into `DATABASE_URL` — bypasses row‑level security. Policies would exist, be visible in
the dashboard, be listed by `pg_policies`, and never once be consulted. That failure mode is worse
than having no policies at all, because it reads as protection.

So migration `004` creates `watcher_app`: `NOBYPASSRLS`, not a table owner, `NOLOGIN` until a deploy
gives it a password. The migration deliberately does not set that password — a credential in a
migration is a credential in the repository.

Three more things follow from the same suspicion:

* **`FORCE ROW LEVEL SECURITY`, not just `ENABLE`.** An owner is exempt from its own table's
  policies. In the self‑hosted tier the application may well own its schema, and "same code,
  different topology" (v1.2 §10) has to mean the isolation survives the topology change.
* **RLS on the tables with no tenant at all** — `eval_runs`, `alembic_version` — with no policy for
  `watcher_app`. They are closed to the application because it has no business in them. The larger
  effect is on Supabase's `anon` role, which PostgREST exposes to anyone holding the publishable
  key: every table in `public` was readable through the REST API by default. `REVOKE ALL … FROM
  anon, authenticated` says so directly, and RLS says it again.
* **The policy fails closed.** `app.current_tenant()` returns `NULL` when the setting is absent, and
  `tenant_id = NULL` is never true. A session that forgets to identify itself sees an empty
  database — not everyone's.

### Where the tenant comes from

Every port in this codebase already took `tenant_id` as an argument. What was missing was anywhere
to *put* it other than a `WHERE` clause. `Database.tenant_session(tenant_id)` is that place: it
stamps `app.current_tenant` on the transaction (via `set_config(…, is_local => true)`, so the
setting cannot outlive the transaction and reach the next tenant through the pooler), and every
adapter that touches tenant data now takes a `TenantScope` rather than a `SessionScope`.

The type change is the point. A future adapter cannot open a session over tenant data without being
handed a tenant — not by convention, but because the callable takes an argument.

### The one exception

`ChannelConfigTenantResolver` answers "which tenant owns this endpoint". It cannot know the tenant;
that is the question. It keeps the unstamped `SessionScope`, and `channel_configs` carries a second
policy:

```sql
CREATE POLICY endpoint_lookup ON channel_configs
    FOR SELECT TO watcher_app
    USING (app.current_tenant() IS NULL);
```

Only when no tenant is set, and only for reads. A session that has adopted a tenant sees that
tenant's endpoints and no others; a session that has not sees endpoint rows and *nothing else in the
database*, because every other policy fails closed on the absent setting. The blast radius is one
table of routing configuration, which is the smallest exception that answers the question.

The alternatives considered and rejected: a blanket read policy on the table (opens it permanently,
including to sessions that have a tenant); `BYPASSRLS` on the app role for that one query (there is
no such thing as "for one query"); a `SECURITY DEFINER` function returning just the id (defensible,
and the right answer if `channel_configs` ever holds per‑tenant secrets — worth revisiting at E‑track
when it does).

### What was verified, and how

Outbound Postgres is blocked from the build environment, so the live check ran through the Supabase
SQL API with `SET LOCAL ROLE watcher_app` — which switches `current_user`, and therefore makes the
policies apply exactly as they would to the application:

| Check | Result |
|---|---|
| As tenant A, `SELECT body_text FROM messages` (no tenant filter) | `mine` — only A's row |
| As tenant B, same query | `not yours` — only B's row |
| As A, `INSERT` a row stamped B | `ERROR 42501: new row violates row-level security policy` |
| No tenant set: messages / tenants / conversations | `0 / 0 / 0` |
| No tenant set: `channel_configs` | the one endpoint row, readable |

`apps/api/tests/test_rls.py` holds the same claims as tests. The cross‑tenant ones need a Postgres
and are skipped unless `WATCHER_RLS_DATABASE_URL` is set; the ones that run everywhere assert the
layer that would rot silently — that each adapter opens its session *as* the tenant it was given.
An adapter that forgot would pass every other test in the tree.

## 4. B3 — building it found two bugs the test suite could not

The Dockerfile lives at `apps/api/Dockerfile` because `.github/workflows/cd.yml` has been checking
that exact path since it was written; the image job is dormant until the file exists and activates
on merge. It builds from the repository root, installs the project (so `pyproject.toml` is the only
dependency list), and runs `uvicorn … --factory` as `nobody`.

Installing it as a package is what surfaced both defects:

1. **`intents.yaml` was not in the wheel.** `packages/intents/schema.py` reads the vocabulary off
   disk relative to its own file. The image imported cleanly right up to `classifier/prompt.py`,
   which builds the system prompt at import time, and died on a missing file. Fixed by declaring it
   as package data — along with `clients/*.yaml`, which the same loader takes.
2. **Starlette 1.0 removed `add_event_handler`.** CI pins `fastapi==0.115.0`; `pyproject.toml`
   allows `>=0.115,<1`, and an image built today resolves 0.141 / Starlette 1.6. The composition
   root registered its shutdown with the removed method, so the container would have started, wired
   everything, and crashed on the last line of `assemble`. Shutdown is now a `lifespan` context
   manager passed to `create_app` — the supported form, and one that works on both versions.

Neither is visible from a test suite that installs pinned versions and imports from the source tree.
Both would have been visible on the first deploy, at the worst possible moment.

## 5. The deploy, and what is still not done

`watcher-api` — Frankfurt, free plan, auto-deploying from `main` on the native Python runtime
(`pip install .`, then `uvicorn … --factory`). The Dockerfile ships regardless: `cd.yml` publishes
the image to GHCR, and it is the artefact the self-hosted tier needs. Moving the service itself onto
the Docker runtime is a dashboard change whenever that is preferred.

Four deploys, and the three failures are the interesting part — each was a gate doing its job. Two
`build_failed` against the pre-merge `main`, which has no `[build-system]` and so cannot be
`pip install`ed. Then `update_failed`:

```
apps.api.core.settings_base.ConfigError:
  Missing required environment variable: ANTHROPIC_API_KEY. See .env.example.
```

That is A1's per-subsystem check refusing to start a process that could accept a message it cannot
classify — at startup, before a guest is waiting, which is the whole reason it is written that way.

**Still open:**

* **The pooler host is unverified.** `DATABASE_URL` was set to `aws-1-eu-central-1`; the build
  environment cannot reach Postgres to confirm it, and SQLAlchemy connects lazily, so a clean
  startup proves nothing. The first tenant query is the test.
* **Sending is degraded.** `no send credentials configured` at startup: replies are composed and
  recorded, and not delivered, until `WHATSAPP_ACCESS_TOKEN` and `WHATSAPP_PHONE_NUMBER_ID` are set.
* **The endpoint is still a placeholder** — step 1 below.
* **B4** (domain, TLS, webhook subscription) — nothing routes a guest to the service yet.

**G3** (emergency detection) is unchanged and is now the most urgent item on the board. See the
handoff: the system answers, and answering a gas leak with a polite note about maintenance is worse
than filing it in silence.

## 6. Deploy runbook

The database is provisioned and migrated; these are the steps between here and a URL Meta can post
to.

1. **Replace the placeholder endpoint** with the Meta phone‑number id (not the phone number):

   ```sql
   UPDATE channel_configs
      SET external_id = '<WHATSAPP_PHONE_NUMBER_ID>'
    WHERE external_id = 'PLACEHOLDER_WHATSAPP_PHONE_NUMBER_ID';
   ```

2. **The service** — done: `watcher-api`, Frankfurt (co‑located with the database), branch `main`,
   build `pip install .`, start
   `uvicorn apps.api.main:create_application --factory --host 0.0.0.0 --port $PORT`,
   `PYTHON_VERSION=3.13.5`. Worth setting its health check path to `/health`; Render currently pings
   `/`, which correctly 404s.

3. **Environment.** `DATABASE_URL` is the *transaction pooler* URI (port 6543), not the direct one:
   the direct host resolves to IPv6 only and Render's outbound is IPv4. The username is the app
   role, dotted with the project ref:

   ```
   postgresql://watcher_app.qjpjxspycuafqqgudsiv:<password>@<pooler-host>:6543/postgres
   ```

   Take `<pooler-host>` from Supabase → Connect → Transaction pooler; it is `aws-N-eu-central-1
   .pooler.supabase.com` and the `N` is per‑cluster, so copy it rather than assuming. `DATABASE_URL`
   is read by both the application and `alembic/env.py`, and the driver rewrite in `db/engine.py`
   means the bare `postgresql://` scheme from the dashboard is correct as pasted.

   Also required, or the process refuses to start (by design — A1 checks per subsystem):
   `META_APP_SECRET`, `META_WEBHOOK_VERIFY_TOKEN`, `ANTHROPIC_API_KEY`. Optional but needed to
   actually deliver a reply: `WHATSAPP_ACCESS_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID` — without them the
   app starts, warns, composes and records replies, and cannot send them.
   `DATABASE_POOL_MODE` defaults to `transaction`, which is what the pooler URI needs.

4. **Migrations on deploy.** `alembic upgrade head` from the image, against the same `DATABASE_URL`.
   The database is already at `004`, so today this is a no‑op that proves the wiring.

5. **Rotate the app role's password** if the one generated during setup should not be trusted:

   ```sql
   ALTER ROLE watcher_app WITH PASSWORD '<new>';
   ```

   Then update `DATABASE_URL`. Nothing else holds it.

6. **B4** — the webhook subscription, pointed at `https://<host>/webhook` — singular, and no
   channel in the path, because `ingestion/router.py` registers `GET`/`POST /webhook` on a router
   with no prefix. Verify it before handing the URL to Meta:

   ```
   https://<host>/webhook?hub.mode=subscribe&hub.verify_token=<token>&hub.challenge=hello
   ```

   which echoes `hello` when the token matches and returns `403 verification failed` when it does
   not. A bare `GET /webhook` in a browser also returns 403 — three query parameters are missing,
   which is the endpoint working rather than failing.

   **No custom domain is required.** Meta needs a publicly reachable HTTPS URL with a trusted
   certificate on port 443, and Render provides exactly that on `*.onrender.com`. A subdomain
   (`api.automera.co` CNAME'd to the service) is a later cosmetic improvement; the webhook URL is
   machine-facing and no customer ever sees it. What *does* matter before a real number: the free
   plan spins down after ~15 minutes idle and takes 30–60s to wake, which Meta sees as a timeout
   and retries. Move to a paid instance first.

### Operational note

`postgres` was granted membership in `watcher_app`, so support can see exactly what the application
sees:

```sql
SET LOCAL ROLE watcher_app;
SELECT set_config('app.current_tenant', '<tenant-uuid>', true);
-- now every query returns what that tenant would get
```

Without the `SET LOCAL ROLE`, the dashboard's own `postgres` connection bypasses RLS and shows
everything — which is convenient, and is exactly why it must not be what the application uses.
